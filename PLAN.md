## 🔒 DESIGN FREEZE — BINDING CONSTRAINT ON EVERY WORKSTREAM

**The existing design is not to be changed. At all.** Not the colours, not the button
styles, not the typography, not the spacing, not the layouts, not the way anything is
presented in the admin portal or any other portal. Every item in this plan is an
**additive implementation in the existing visual language** — never a redesign.

**Concretely, this means:**

| Rule | What it means in practice |
|---|---|
| **Reuse, never re-style** | New UI uses the existing primitives: `ui/button.tsx` (its existing variants only), `ui/dialog.tsx`, `ui/input.tsx`, `ui/table`, `shared/SpecTable.tsx`, `AdminTable`, `AdminPageHeader`, `PortalShell`, `FabricCard`. Do not author new button styles, new card treatments, or new modal chrome. |
| **No new design tokens** | Use only the palette in `src/index.css` `@theme` (`background`, `surface`, `elevated`, `card`, `accent` `#E8593C`, `border-cream`, etc.) and the existing fonts (Inter / DM Sans / IBM Plex Mono). No new colours. No new type scales. |
| **Admin portal keeps its exact look** | New admin surfaces (video upload, change-request review) drop into the existing `AdminTable` / `AdminPageHeader` patterns, in the current dark shell. The admin UI's structure and presentation stay identical. |
| **Supplier & buyer portals keep their exact look** | New pages (supplier product edit, catalogue builder, buyer wishlist) render inside the existing `PortalShell` with the existing nav, spacing and card treatments. |
| **New components match existing anatomy** | The wishlist comparison table follows the existing table patterns; the wishlist modal follows the existing `Dialog`; the attachment chip follows the existing `font-mono` / `border-cream` chip idiom. |
| **Motion stays on the existing tiers** | `src/lib/motion.ts` only — `fadeUp`, `cardHover`, `pageTransition`. No new animation vocabulary. |

**The one place this plan touches visual presentation, it is a bug fix, not a redesign:**

- `max-h-[82vh]` → `max-h-[82dvh]` in `FilterDock.tsx` — a **one-word fix for content being
  cut off below the fold**. It changes no styling; it makes the existing design actually
  fit on a phone.
- Moving the marketplace search input out of the filter drawer is a **placement** change
  requested to fix discoverability. It reuses the existing input styling verbatim. **If you
  want the search to stay exactly where it is, say so and it will not move** — it is the only
  layout change in the plan and it is optional.

**Anything in a review finding that reads as a design opinion — "kill the bobbing chevron",
"rename Refine selection to Filters", "don't use a red heart", "collapse the dock into the
toolbar on desktop" — is NOT adopted.** Those are recorded in the review section as
observations only. The design stays as built.

## Premise challenge (Phase 1 · Step 0A)

### ❌ PREMISE 1 IS FALSE — "we need a separate proper admin panel at /admin"

**A full admin panel already exists at `/admin` with 14 routes**: dashboard, live monitor,
messages, products (full CRUD + publish + featured), suppliers (verify/suspend), buyers,
users (create any-role accounts, reset passwords — via the `admin-users` edge function),
listing pipeline, attributes, inquiries, settings. It is not missing.

The real bug is a three-line auth defect:

1. `AuthGuard.tsx:39` — when logged out, stashes the URL you hit into `state.from`:
   ```tsx
   return <Navigate to={fallbackPath} state={{ from: location.pathname }} replace />
   ```
2. `LoginPage.tsx:24-28` — honours that `from` **without checking it against your role**:
   ```tsx
   const target = from && !from.startsWith('/auth') ? from : ROLE_HOME_PATHS[role]
   ```
3. `src/types/app.ts:377-380` — admin passes **every** zone check, so nothing bounces
   them out:
   ```ts
   export function canAccessZone(role: UserRole, zone: PortalZone): boolean {
     if (role === 'admin') return true
     return role === zone
   }
   ```

So: an admin who touches any `/supplier-portal/*` URL while logged out (bookmark, stale
tab, expired session) logs in and lands **inside the supplier portal, wearing the
supplier shell**. That is exactly the reported symptom. React Router persists that
history state, so it survives reloads — which is why it feels intermittent.

**Fix: validate `from` against the role before honouring it.** ~5 lines. Building a
second admin auth portal would add a second auth surface to maintain and would not fix
this bug — the same stale `from` would still redirect.

**Recommendation: reject the "separate admin panel" framing. Fix the redirect.**
Optionally add `/admin` → `/admin/dashboard` and an `/admin/login` alias that pre-clears
`from`, purely for muscle memory.

### ⚠️ PREMISE 2 IS PARTLY FALSE — "supplier portal only allows stock and price"

True of the Inventory page (`supplier/InventoryPage.tsx:63-72` writes only
`stock_meters`, `price_min_pkr`, `price_max_pkr`). But suppliers already submit listing
requests, build invoices, and edit their brand/profile.

More importantly: **the restriction is cosmetic.** RLS
(`products_supplier_update`) lets a supplier UPDATE *every* column of their own
products, including `status`, `visibility`, and `price_approved`. A supplier can
self-approve their own pricing today with a curl command.

This inverts the task. "Let suppliers edit more fields" is not about *loosening* — the
backend is already wide open. It is about **adding the column-level guard that was
never there**, then deliberately opening the fields you actually want.

### ✅ PREMISE 3 IS SOUND, but a mechanism already exists — private products

`visibility` and `product_private_domains` already exist and are already enforced in the
`products_public_read` policy. Today's mechanism gates private products by the **buyer's
email domain**. You want **shareable links**. These are different trust models and both
are legitimate; the plan proposes adding link-tokens *alongside* the domain gate.

### ✅ PREMISE 4 IS SOUND — chat attachments don't work

Root cause: **the `message-attachments` bucket does not exist.** The `attachments` jsonb
column, the `MessageAttachment` TS type, and an admin-side *renderer* that displays
attachments all exist. The upload path and the send path do not
(`MessageInput.tsx:58-72` is hard-`disabled` with an "Attachments coming soon" label;
`ChatThread.tsx:116-133` drops the attachments argument on the floor).

Two landmines: the documented bucket RLS keys off `'path'` but the TS type uses `'url'`
— they disagree. And `support_messages` has **no attachments column at all**.

### ⚠️ PREMISE 5 NEEDS A DECISION — marketplace filters

The requested filters split into three very different classes:

| Filter | Data today | Work required |
|---|---|---|
| Colour, supplier, category, price | ✅ real columns, server-side | Already works |
| Stock | ✅ `stock_meters` column | Trivial |
| **GSM, width, composition** | ❌ **nowhere** (EAV empty) | Schema + **backfill from products.json** |
| **MOQ, lead time** | ⚠️ columns exist, **100% NULL** | Backfill or supplier data entry |
| **3D availability** | ⚠️ `scan_files` exists, **0 products have any** | Filter would match nothing |
| **Sample availability** | ❌ no field anywhere | New column + who sets it? |

Also a live correctness bug: **GSM is filtered client-side *after* pagination**
(`useProducts.ts:47-68`), so the result count and the "Show N fabrics" button are wrong
whenever a GSM filter is active, and pages come back short.

**Recommendation: promote the hot filter fields to real columns on `products`** (`gsm`,
`width_inches`, `composition`, `has_3d`, `sample_available`) rather than filtering
through an empty EAV table. Backfill GSM/width/composition from `products.json`. This
makes every filter server-side and correct. The EAV stays for long-tail attributes.

**But MOQ, lead time, 3D and sample availability have no data.** Shipping those filters
means shipping four filters that match nothing until someone enters the data. That is a
product decision, not an engineering one — see the gate.

### ✅ PREMISE 6 IS SOUND — mobile filter modal won't scroll (root cause found)

`FilterDock.tsx:240-252` puts a framer-motion `drag="y"` on the drawer container.
Framer-motion sets `touch-action` on **any** element with a `drag` prop, regardless of
`dragListener={false}` (`framer-motion/.../use-props.mjs:43-46`):

```js
style.touchAction = props.drag === true ? "none" : `pan-${props.drag === "x" ? "y" : "x"}`;
```

The drawer therefore renders with `touch-action: pan-x`, which kills vertical panning
across the entire subtree — so the `overflow-y-auto` body at line 290 never scrolls on
touch. It scrolls fine with a mouse wheel, which is why it looks desktop-only-OK.

Compounding: `max-h-[82vh]` should be `82dvh` (mobile browser chrome makes the drawer
taller than the visual viewport), and the search input is the **last** element in a
single-column stack — so it is exactly what falls below the fold. Body scroll is also
locked while open, so there's no fallback.

**Fix is ~3 lines.** This is the cheapest, highest-visibility win in the whole batch.

### ✅ PREMISE 7 IS SOUND — analytics need more depth, with one catch

`supplier_page_views` exists (66 rows) and `AnalyticsPage.tsx` already shows live
visitors, 7d/30d views, visiting companies, and top-5 fabrics. Extending it is real work
but well-founded. Three catches:

- **Views are page-loads, not uniques** — `trackSupplierView()` has no dedupe/throttle,
  so every refresh inserts a row.
- **The numbers are forgeable** — `WITH CHECK (true)` for `anon`.
- **"Locations" is not capturable today.** No IP, no geo, no country is stored anywhere.
  This needs new capture (edge function doing IP→geo at write time) and carries privacy
  implications. It is the only analytics ask that isn't a query away.

### ✅ PREMISE 8 IS SOUND — wishlist

Nothing exists. `cart_items` (unique on `(buyer_id, product_id)`) is a near-exact
template. Cleanest item in the batch. Open question in the gate: **anonymous wishlists?**

### ✅ PREMISE 9 IS SOUND — admin video upload

No video column, no bucket, no player. Straightforward additive work.

## The plan

Six workstreams. W1 is a prerequisite for W5 (analytics integrity) and W3 (supplier
edit needs the guard). Everything else is independent and parallelisable.

### W1 — Auth & permission correctness `[P1 · CC ~1h · human ~1d]`

Fixes the reported admin-lands-in-supplier-portal bug **and** closes a live privilege
hole found during intake.

1. **`src/pages/auth/LoginPage.tsx:24-28`** — only honour `from` if its zone matches the
   signed-in role; otherwise fall back to `ROLE_HOME_PATHS[role]`.
   ⚠️ **Naive version breaks every non-portal deep link.** `isPortalZone` returns `null`
   for anything outside `/admin`, `/supplier-portal`, `/buyer` — so `fromZone === role`
   is false for `/cart`, a shared product URL, etc., and bounces the user to their
   dashboard instead of where they were going. Accept `null` zones:
   ```ts
   const fromZone = from ? isPortalZone(from) : null
   const target = from && !from.startsWith('/auth') && (fromZone === null || fromZone === role)
     ? from
     : ROLE_HOME_PATHS[role]
   ```
   Note: **step 2 (strict `canAccessZone`) is what actually closes the hole** —
   `AuthGuard.tsx:50` would then bounce the admin out of `/supplier-portal/*` regardless
   of `from`. Step 1 is defence in depth. If scope must be cut, keep step 2.
2. **`src/types/app.ts:377-380`** — make `canAccessZone` strict (`role === zone`). Admins
   stop silently inhabiting the supplier/buyer shells.
3. **`src/components/layout/PortalShell.tsx:100`** — zone is currently derived from the
   URL path with a `?? 'buyer'` fallback. Derive from role instead.
4. Add the missing **`/auth/pending`** route (`AuthGuard.tsx:47` redirects to a route
   that does not exist → falls through to `*` → `/`).
5. Add `/admin` → `/admin/dashboard` redirect.
6. **🔒 Close the privilege hole.** Today a supplier can self-approve their own pricing
   with a single API call.

   **A `BEFORE UPDATE` trigger is the correct mechanism — column-level GRANTs cannot work
   here.** Supabase runs *every* logged-in user, supplier and admin alike, as the same
   Postgres role `authenticated`. "Admin" is a row in `profiles`, not a DB role. So
   `revoke update(price_approved) from authenticated` would lock **admins** out too. RLS
   `WITH CHECK` can't do it either — it has no access to `OLD`.

   Three things the naive trigger gets wrong:
   - **Reject, don't revert.** A reverting trigger returns HTTP 200 with a quietly-mutated
     row — silent data loss, and it contradicts our own test ("must be rejected"). Use
     `raise exception ... using errcode = '42501'`.
   - **Exempt `service_role`.** Triggers fire for `service_role` (only *RLS* is bypassed),
     and it has no `auth.uid()`, so `is_admin()` returns false. Without an exemption the
     seed script, the GSM backfill and the admin edge functions all start failing.
   - **The guard list was incomplete.** It must also cover **`is_featured`** — a supplier
     can currently `PATCH is_featured=true` and put themselves on the homepage carousel —
     plus `view_count`, `inquiry_count`, `slug`, `published_at`, `created_by`.

   ```sql
   create or replace function guard_product_admin_columns()
   returns trigger language plpgsql security definer set search_path = '' as $$
   begin
     if auth.role() = 'service_role' or public.is_admin() then
       return new;
     end if;
     if new.price_approved    is distinct from old.price_approved
        or new.price_approved_by is distinct from old.price_approved_by
        or new.price_approved_at is distinct from old.price_approved_at
        or new.status         is distinct from old.status
        or new.supplier_id    is distinct from old.supplier_id
        or new.is_featured    is distinct from old.is_featured
        or new.slug           is distinct from old.slug
        or new.published_at   is distinct from old.published_at
        or new.view_count     is distinct from old.view_count
        or new.inquiry_count  is distinct from old.inquiry_count
     then
       raise exception 'not permitted to modify admin-controlled columns'
         using errcode = '42501';
     end if;
     -- Any price change re-opens approval. Enforced here, NOT in the UI:
     -- InventoryPage.tsx:63-72 currently sets price_approved=false in JS, which a raw
     -- API call trivially bypasses.
     if new.price_min_pkr is distinct from old.price_min_pkr
        or new.price_max_pkr is distinct from old.price_max_pkr then
       new.price_approved := false;
     end if;
     return new;
   end $$;

   create trigger products_guard_admin_columns
     before update on products
     for each row execute function guard_product_admin_columns();
   ```

> If we ship the supplier-edit screens (W3) *without* step 6, we widen a hole that is
> already open. W1 must land first.

### W2 — Marketplace filters + the mobile scroll bug `[P1 · CC ~3h · human ~3d]`

**2a. Mobile drawer scroll — ⚠️ ROOT CAUSE RETRACTED. DO NOT SHIP A FIX YET.**

> **My original diagnosis was wrong and I verified it wrong.** I claimed framer-motion
> stamps `touch-action: pan-x` on the drawer. The actual installed source
> (framer-motion 12.40.0, `use-props.mjs:34`) guards it:
> ```js
> if (props.drag && props.dragListener !== false) {   // ← I omitted this line
>     style.touchAction = props.drag === true ? "none" : `pan-${...}`;
> }
> ```
> `FilterDock.tsx:246` sets `dragListener={false}`. **The branch never executes.**
> `touchAction` is assigned in exactly one place in the whole library, and that place is
> unreachable here. The proposed `style={{ touchAction: 'auto' }}` override would have
> been a no-op — and would also have lost to framer's assignment even if it had fired,
> since `useStyle()` copies the user's style first and framer overwrites after.

**The scroll bug is therefore UNDIAGNOSED.** Reproduce on a real 375×667 touch device
before writing a line of code. Live suspects, none confirmed:
- **Lenis** is instantiated app-wide (`SmoothScroll.tsx:15`, `smoothWheel: true`) and
  there is **no `data-lenis-prevent`** anywhere in the tree. The drawer is
  `createPortal`ed to `document.body`, *outside* the `SmoothScroll` wrapper.
- iOS `body { overflow: hidden }` scroll-locking (`FilterDock.tsx:125-132`) is famously
  unreliable on Safari.

**What IS confirmed and worth shipping regardless (independent of the scroll question):**
- `max-h-[82vh]` → `max-h-[82dvh]`. With mobile browser chrome visible, `82vh` makes the
  drawer taller than the *visual* viewport while `bottom-0` anchors it to the *layout*
  viewport — so the sticky footer and the tail of the content sit below the fold. **This
  alone explains the "search bar remains half hidden" symptom.**
- The search input is the **last** element of a single-column stack — the first thing to
  fall off. Move it out of the drawer entirely (see 2e).

**2b. Promote hot filter fields to real columns.**
```sql
alter table products
  add column gsm numeric,
  add column width_inches numeric,
  add column composition text,
  add column sample_available boolean not null default false,
  -- has_3d: the naive form `jsonb_array_length(scan_files) > 0` compiles, but HARD-FAILS
  -- on any non-array scan_files ("cannot get array length of a non-array"). scan_files has
  -- NO check constraint forcing array-ness, so one bad write = a write outage on products.
  add column has_3d boolean generated always as (
    case when jsonb_typeof(scan_files) = 'array'
         then jsonb_array_length(scan_files) > 0
         else false end
  ) stored,
  add constraint products_scan_files_is_array check (jsonb_typeof(scan_files) = 'array');

create index products_gsm_idx on products (gsm) where status = 'published';
-- pg_trgm is NOT installed on this project (verified: pg_extension has only plpgsql,
-- pg_stat_statements, uuid-ossp, pgcrypto, supabase_vault). gin_trgm_ops would error.
-- If composition is a FACET (checkbox: Cotton / Polyester), skip trigrams entirely and
-- use a btree on a normalized value. Only install pg_trgm if you need ILIKE '%…%'.
create index products_composition_idx on products (composition);
```
**2c. Backfill** from `products.json` (205 rows). GSM must be parsed out of
`"364 GSM | 10.75 Oz"` — regex `/(\d+(?:\.\d+)?)\s*GSM/i`. Width is `"Width (Inches)"`.
Composition is `"Fabric Content"`. Write the backfill as a **migration + idempotent

### W3 — Supplier product editing + private catalogues `[P1 · CC ~5h · human ~1w]`

**3b. Private catalogues with shareable links.**
```sql
create table catalogues (
  id uuid primary key default gen_random_uuid(),
  supplier_id uuid not null references suppliers(id) on delete cascade,
  name text not null,
  -- `base64url` is NOT a valid encode() format here (verified: errors with
  -- `unrecognized encoding`; it only lands in PG18). Plain base64 emits `+ / =` — and
  -- the token is a PATH SEGMENT (/c/:token), so a `/` would split the route.
  -- gen_random_bytes is pgcrypto: schema-qualify it, or a `search_path = ''` migration fails.
  share_token text unique not null
    default encode(extensions.gen_random_bytes(24), 'hex'),   -- 48 chars, 192 bits, path-safe
  is_active boolean not null default true,
  expires_at timestamptz,
  created_at timestamptz not null default now()
);
create table catalogue_products (
  catalogue_id uuid references catalogues(id) on delete cascade,
  product_id uuid references products(id) on delete cascade,
  primary key (catalogue_id, product_id)
);
```
- Public route `/c/:token` renders the catalogue **without login**. Token is 24 random
  bytes (192 bits) — unguessable, revocable (`is_active`), expirable.

**⚠️ My first RLS design was self-contradictory. Corrected:** it said both "extend
`products_public_read` so a product is readable when the token is presented" *and*
"validate via a `SECURITY DEFINER` RPC". Those are mutually exclusive — a `SECURITY
DEFINER` function runs as the owner and **bypasses RLS entirely**, so extending the
policy would be dead code. An anon client also cannot hand a value to an RLS policy at
all (no `set_config` from PostgREST, no custom claims on an anon JWT).

**Pick the RPC route, and only the RPC route:**
```sql
create function get_catalogue(p_token text)
returns setof products
language sql stable security definer set search_path = '' as $$
  select p.* from public.products p
  join public.catalogue_products cp on cp.product_id = p.id
  join public.catalogues c on c.id = cp.catalogue_id
  where c.share_token = p_token
    and c.is_active
    and (c.expires_at is null or c.expires_at > now());
$$;
```
- **🔒 `share_token` must NEVER be SELECT-able by `anon`.** `revoke all on catalogues from
  anon` — no anon policy at all. The moment anyone adds a "reasonable" policy like
  `using (is_active and expires_at > now())`, a single
  `GET /rest/v1/catalogues?select=share_token` with the **public** anon key dumps **every
  private share link for every supplier**. This is the single most dangerous line in the
  plan.
- `catalogue_products` needs its own RLS policy (mine specified none) and an index on
  `product_id`.
- Hidden cost not in the original estimate: the RPC must re-implement the join shape of
  `PRODUCT_LIST_SELECT` (`useProducts.ts:17`), so `/c/:token` **cannot reuse `useProducts`**.
- Don't leak "expired" vs "revoked" vs "never existed" as distinguishable errors.
- The existing `product_private_domains` gate stays untouched and keeps working.
- Supplier UI: build a catalogue, toggle products in, copy link, revoke (**with a confirm
  step** — revoke is irreversible for every recipient at once).

### 🔴 The elephant: a "private" catalogue is not private

`product-images` is a **public bucket** with **no size limit and no mime allowlist**
(verified: `storage.buckets` has exactly one row, `public = true`). **Every image of every
`visibility='private'` product is already world-readable at a stable CDN URL.** Revoking a
share token revokes the *listing*, not the *images* — anyone who ever loaded the link keeps
working image URLs forever.

Decide explicitly, and write the decision down:
- **(a)** Accept it — the images leak, the *specs and pricing* are what's protected. Cheap,
  and defensible for a fabric catalogue.
- **(b)** Move private-product images to a private bucket with signed URLs. Correct, and
  materially more work.

Either way, **set `file_size_limit` and `allowed_mime_types` on `product-images` now.**
It's a one-line fix and it's the same hole we're careful about for video (F7).

> ⚠️ Anyone with the link can view. That is the point, but it means the link **is** the
> credential. Log accesses; make revocation one click.
